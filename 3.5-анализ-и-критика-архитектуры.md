- Проверь конкурентность: гонки, блокировки, порядок операций при параллельных запросах
- Проверь границы ответственности: нет ли дублирования логики между сервисами/слоями
- Проверь API и схемы: единообразие контрактов, валидация связей, права доступа
- Проверь тестируемость: можно ли проверить критичные риски из дизайна тестами
- Выяви архитектурно значимые юзкейсы, которые дизайн не покрывает или покрывает слабо

Проверка юзкейсов (обязательный блок — пройди явно, не пропускай):
- Выпиши из 01_task.md все сценарии, роли и сценарии из раздела «Исключения» (что не делаем — тоже фиксируй)
- Для каждого сценария проверь: есть ли в 03_design.md ответ на уровне архитектуры (данные, API, состояния, ошибки)?
- Пройди не только happy path: первый раз, пустые данные, повторное действие, отмена/откат, параллельные действия, сбой внешнего сервиса, права доступа
- Ищи сценарии, которые не записаны в ТЗ явно, но вытекают из бизнес-логики (типичные вопросы пользователя «а что если…»)
- Отдельно отметь сценарии, которые дизайн сознательно откладывает (MVP / «потом») — не путай с упущением

Что спрашиваешь у меня (максимум 2-3 вопроса, только если критично):
- Есть ли известные ограничения (сроки, бюджет LLM, обратная совместимость), влияющие на оценку дизайна?
- Какие сценарии для вас наиболее критичны, если дизайн их не закрывает полностью?
